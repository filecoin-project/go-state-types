# go-state-types agent guide

go-state-types is the Go mirror of Filecoin's built-in actor types: state, params, returns and method tables for actors v8 and later, plus the state migrations that run at each network upgrade. Lotus decodes chain state, messages and traces with these types and runs these migrations, so an encoding mismatch or a migration bug is a consensus or API bug in every Go node.

## Where go-state-types sits in Filecoin

- [builtin-actors](https://github.com/filecoin-project/builtin-actors) is the source of truth. Each `builtin/vN/` mirrors the builtin-actors release that ran on chain byte for byte; check the exact tag, since patch releases change types. Its `AGENTS.md` holds the encoding rules on the Rust side. Earlier actors versions live in specs-actors.
- Proof identifiers in `abi/sector.go` follow rust-fil-proofs, and miner `policy.go`, `monies.go` and `util/smoothing` follow that version's Rust policy and formulas. Lotus and SP software compute pledge and fees from them, so their tests compare exact integer output, including rounding, with the Rust tests they cite.
- [Forest](https://github.com/ChainSafe/forest) writes its own migrations in Rust; both must produce the same state root.
- [Lotus](https://github.com/filecoin-project/lotus) pins one go-state-types release and imports every version through it: actor wrappers (`chain/actors/builtin/<actor>/`, generated by `make actors-gen`), the method registry that decodes params and traces (`chain/actors/builtin/registry.go`), migrations wired in `chain/consensus/filcns/upgrades.go`, JSON-RPC API types, and `lotus-shed` tooling. Its `documentation/misc/Building_a_network_skeleton.md` (go-state-types checklist) is the per-upgrade procedure.

For a change to a shared type, an old version, a method table or a JSON shape, trace the affected Lotus callers and state in the PR which applies: a dependency bump alone (a corrected codec or method entry), a companion Lotus change, or a JSON-RPC compatibility decision (a mirrored field change can alter the API while Lotus still compiles). Curio, Boost and Venus import these packages too. If a sibling checkout is available, read its `AGENTS.md` before changing a shared contract.

## Layout and versions

- `builtin/vN/` holds one actors version: a directory per actor (`*_state.go`, `*_types.go`, `methods.go`, `invariants.go`, generated `cbor_gen.go`), `util/adt/`, `migration/` (the migration into vN), `check.go` and `gen/`.
- Shared packages (`abi`, `big`, `builtin/*.go`, `migration`, `exitcode`, `proof`, `manifest`, `crypto`, `batch`, `network`, `actors` and others) are imported by every version, so a change there reaches all of them. `actors.VersionForNetwork` maps network versions to actors versions, and some network versions share one.
- A new upgrade starts by copying the previous `builtin/vN/` to `vN+1`, rewriting import paths and reducing `migration/` to `system.go` and `top.go`, per the Lotus checklist. A migration into vN decodes with the previous version's packages and builds vN's; check each import path rather than its alias, which can name the wrong version.
- One module holds every version, so an edit to an old `vN` ships in the next release. Touch an old version only to make it match the bundle that ran (a wrong param type in a `Methods` map, a type missing from codegen), and change every affected copy. Expect downstream breakage: Lotus aliases some of its types to specific versions, and newer migrations import older packages.

## Encoding

- Types encode as DAG-CBOR tuples through cbor-gen (`WriteTupleEncodersToFile` in each `gen/gen.go`); field order is wire order and must match the Rust struct. `cbor_gen.go` is generated: edit the struct, list new types in `gen.go`, and run `make gen`, which regenerates every version. cbor-gen only generates codecs for types listed in `gen.go`; a `Methods` entry whose param type isn't listed panics Lotus's `StateEncodeParams`.
- Types whose wire form cbor-gen can't express have hand-written `MarshalCBOR` outside `cbor_gen.go`; keep them out of `gen.go`.
- `big.Int` encodes as bytes: a sign byte then the big-endian magnitude, zero as empty bytes; a nil `*big.Int` encodes as null and an unset value as zero. `cborgen:"transparent"` matches Rust `#[serde(transparent)]`.
- `cborgen:"optional"` on a trailing field is the Go half of a lazy migration, a last resort; see builtin-actors `AGENTS.md`.
- Golden hex vectors in `*_types_test.go` pair with Rust serialization tests. A new or changed type gets a vector here and in builtin-actors. Take expected bytes from Rust or chain data, not a Go round trip: a Go writer and reader can agree while both disagree with Rust. For an optional trailing field, test that the short tuple decodes and that writing it produces the long one.
- JSON is Lotus's JSON-RPC shape: `big.Int` marshals as a decimal string, and `DealLabel` has its own `MarshalJSON`. Renaming or retyping an exported field, or changing a marshaller, changes the Lotus API.

### Method tables

- `builtin/vN/<actor>/methods.go` maps each method number to a name and param and return types for that version's bundle. Lotus decodes params, returns and traces of historical messages from these maps, so a wrong entry silently mis-decodes history.
- A new exported method gets its FRC-0042 number from `MustGenerateFRCMethodNum`, an entry in that version's `methods.go`, and a field in the unversioned `MethodsX` struct in `builtin/methods.go`.

## HAMT and AMT

- `builtin/vN/util/adt/` wraps go-hamt-ipld v3 (`Map`, `Set`, `BalanceTable`) and go-amt-ipld v4 (`Array`), with `Multimap` and per-actor helpers such as market's `SetMultimap`.
- HAMT blocks don't record their bitwidth, and the AMT library rejects a mismatched one. Use the structure's named constant (`StatesAmtBitwidth`, `CronQueueHamtBitwidth`, `builtin.DefaultHamtBitwidth`); each must equal the Rust constant for that structure. A HAMT opened with the wrong bitwidth can load and then miss keys.
- Key encoding must match the Rust key type for that version: `abi.UIntKey` is unsigned LEB128 (Rust `u64`), `abi.IntKey` is zigzag (Rust `i64`), `abi.AddrKey` is address bytes and `abi.IdAddrKey` the ID payload. A mismatch reads another key's entry without error: for non-negative e, `IntKey(e)` equals `UIntKey(2e)`.

## Migrations

`builtin/vN/migration/top.go`'s `MigrateStateTree` produces the vN state tree from the previous one; Lotus calls it at the upgrade epoch and in pre-migrations before it.

- It maps every old manifest code to a migrator (by default `CachedMigration(CodeMigrator)`, which swaps the code CID), replaces the system actor's manifest, overrides actors whose state changes, and runs `migration.RunMigration`. The runner fails on any actor code without a migrator.
- A migrator returns only a new code CID and head; the runner keeps balance, nonce and delegated address. Creating actors or changing balances happens on `actorsOut` after the run. `ActorTree` can't delete an actor.
- A state shape change in builtin-actors needs a migrator here in the same upgrade, including key-encoding and bitwidth changes; without one, existing entries become unreachable.
- Every past migration still runs, on devnets, in Lotus itests and when replaying old state. A change to `migration/` or an old `vN/migration/` must leave their output roots unchanged.
- Network-specific inputs arrive as `MigrateStateTree` arguments from the Lotus wiring, and `lotus-shed migrate-state` calls the same function. Read them from arguments, not globals.
- Output must be a pure function of the input state and fixed config. Workers run in parallel and `Deferred()` migrators run afterwards in random order; HAMTs and AMTs are canonical, but shared Go state written by migrators needs a lock, and the store must accept concurrent writes.
- `CachedMigration` runs a migrator only on a cache miss, keyed by (address, head). Pre-migration fills the cache from a recent state; the real migration reuses entries whose head hasn't changed. Don't cache a migrator whose output depends on anything beyond its own state.
- `priorEpoch` is the trigger tipset's height during pre-migration and the upgrade height in the real run, so a migrator that uses it stays uncached. `cfg.UpgradeEpoch` is zero unless the Lotus wiring sets it.
- Caching pays for many or expensive actors (miners); a single cheap actor, or power, whose state changes every epoch, gains little. New cache keys in `migration/util.go` need a prefix of their own.
- A migrator with a cached diff path and a from-scratch path must apply identical predicates; the cached-versus-uncached comparison below catches a mismatch.
- Mainnet state is large, dominated by miner sectors and market deals. Bound memory, avoid per-sector rewrites, report peak memory and time from `migrate-state`, and test on tiny synthetic state as well.
- A Lotus node that already ran a migration returns its stored result (`HandleStateForks`); `lotus-shed migrate-state` uses a fresh migration-result cache.

## Testing

- `go test ./...` covers types, golden vectors, invariants and migration unit tests on synthetic trees.
- Invariants live in `builtin/vN/check.go` and each actor's `invariants.go`, and run on real state: `lotus-shed check-invariants <stateroot> <height>`, which picks the actors version from the height and network schedule. They check the new state only. New state needs invariants here and in builtin-actors; a migration's own invariants are removed in the next version.
- A migration is tested on a snapshot of the target network with a matching `lotus-shed` built against the change: `lotus-shed migrate-state --repo <offline repo> --check-invariants <nv> <blockCID>`. Flags go before the arguments; without `--repo` it locks `~/.lotus`. The block's parent state must precede the upgrade.
- It runs uncached, pre-migrated and cached, and fails if the cached and uncached roots differ. That proves cache agreement, not correctness. It prints invariant violations and still exits 0, so read and report them. For a change to a past migration, compare the output root with the released implementation's on the same input; for a new upgrade, record input and output CIDs for comparison with Forest. State what you ran, the roots and the timings.
- Lotus `itests/migration_test.go` exercises upgrades end to end. To build Lotus against a go-state-types change, point its `go.mod` at it with a `replace` directive.

### Commands

```sh
make gen     # regenerate cbor-gen codecs for every version; CI fails on a diff
make build

make lint    # golangci-lint run ./...
```

## Releases

The minor version is the actors version and the major is always 0 (`README.md`, Versioning); `-dev` and `-rcN` mark unreleased upgrades. A PR that bumps `version.json` runs `.github/workflows/release-check.yml`; merging it runs `releaser.yml`, which tags and publishes.

## Change hygiene

Report suspected vulnerabilities privately through the repository's GitHub security policy, never in a public issue or PR.

### Comments, docs and commit messages

- Write code comments and reference docs year-zero: describe the code as it is, as if it had always been this way. Release notes may compare old and new behaviour. History (old behaviour, the bug, the fix, the issue) goes in the commit message and PR description. In comments, words like "now", "previously", "used to", "no longer", "instead of" and "fixed" signal change narration; rewrite or delete. A link that explains a constraint that still applies stays.
- Each `builtin/vN/` describes one actors version as that bundle runs. Leave change records ("added in v17", "was X") out of it; a comment may explain an oddity the encoding must keep.
- A comment, in code or tests, earns its place by stating what a maintainer can't read from the code: intent, an invariant, a compatibility or consensus constraint, a surprising cost. Don't restate the code, the test name or the assertion; prefer one precise sentence. Public API docs state the contract: inputs, outputs, errors, bounds.
- Commit messages and PR descriptions explain what changed and why, for a reviewer. Skip summaries of the diff, boilerplate sections and claims you haven't verified.

### Pull requests

Use Conventional Commits form, `<type>(<scope>): <description>`, with `!` after the type for a change that breaks importers (`feat!:`, `chore!:`).

## Reviewing changes

Read the matching builtin-actors code, the affected Lotus callers and the tests before commenting, and verify assumptions against current code.

Priorities, in order: encoding parity with Rust; migration correctness and determinism; method tables; key types and bitwidths; downstream API and JSON breakage; tests and invariants.

Comment only on a concrete, plausible failure the change introduces: the triggering input or state, the wrong result, its consequence. Skip style preferences, speculative hardening, pre-existing problems and refactors without behavioural benefit. One exception: this repository treats comments that narrate the change or restate the code as defects, so report them (see Comments, docs and commit messages).

## Maintaining agent context

This file is maintained with the code. When a change makes it wrong, fix it in the same PR. When a change alters a contract with a neighbouring repository, name the follow-up that repository needs, including its `AGENTS.md`, in the PR description.

Each `AGENTS.md` has a sibling `CLAUDE.md` containing only `@AGENTS.md`, because by default Claude Code skips `AGENTS.md` files whenever a `CLAUDE.md` exists at or above its working directory. Add the pair together; put content in `AGENTS.md`, never in the `CLAUDE.md`.
